# Architecture and contracts

This file is the contract between the parts of the system. If you change a shape here, say so loudly in your report.

## What it is
Engineers use Claude Code through a self-hosted **Claude apps gateway** (Anthropic's own, built into the `claude` binary) on Vertex AI.
This repo adds: a **budget app** for admins and engineers (Node backend `api/`, React Native Web UI `app/`), **Terraform** for GCP,
an **installer** for engineers (`client/`), and a local dev stack. Open source, brand-neutral, not affiliated with Anthropic.

## Principles
- **Data is visible, changes are gated.** Read endpoints are open by default (`APP_VIEW_ACCESS=open`; `admin` makes them need a login). Every write needs an admin session.
- **Local-only by default.** The server refuses to listen beyond loopback unless on Cloud Run (private by IAM) or `APP_ALLOW_NON_LOOPBACK=1`.
- **No dependencies in `api/`** (Node 20+, built-ins and `fetch` only). Secrets only from environment. Never log secrets.
- **Org/group caps are per-person defaults, not shared pools.** A personal cap overrides them. `null` amount = unlimited.
- **Honest data.** Never fabricate numbers outside demo mode (`APP_DEMO=1`), which is bannered. Token/cache analytics need client telemetry and are *not* available yet: say so.
- Cloud Run IAM owns the `Authorization` header; the app's own session token travels in `x-app-token`.

## Usage backend (`api/lib/usage/index.mjs` -> `createUsage(cfg, { store }) -> usage`)
```
usage.source            'none' | 'demo' | 'logs' | 'clickhouse'
await usage.ok()        true | false | null (null = not configured)
await usage.roster()    Map(sub -> email|null)
await usage.users(w)    { rows:[{sub,email,requests,ok,lastSeen(iso|null),models[]}], spark: Map(sub -> number[w.n]) }
await usage.detail(sub, w, limit=25)  { series:{models:[..], values:{model:number[w.n]}}, models:[{model,requests,ok,p50|null}], recent:[Recent] }
await usage.company(w)  { totals:{requests,ok,upstream_errors,blocked,rejected,users}, byUser:[{sub,email,requests}], byModel:[{model,requests,ok}], series:{sub:number[w.n]} }
await usage.ingest()    { ingested:number }   // logs backend pulls new gateway log events; others return {ingested:0}
Recent = { ts(iso), id, sub, email, model, outcome, status, ms, lt(bool), cause|null }
```
`none` returns empty shapes (never throws). The aggregation logic is in `usage/aggregate.mjs` (shared by `logs` and `demo`).

## Overrides (`api/lib/overrides.mjs` -> `createOverrides({ store, gateway, cfg, now }) -> o`)
Temporary, automatically-reverting budget boosts (on-call, launch, incident). `o.list({status?})`, `o.forUser(sub)`, `o.create(input, admin)`, `o.cancel(id, admin)`, `o.tick()` (apply due, revert expired).
```
Override = { id, sub, email, name, period:'weekly'|'monthly', extraCents, baseCents, targetCents|null, startsAt(iso), endsAt(iso), reason,
             createdBy, createdAt, status:'scheduled'|'active'|'ended'|'cancelled'|'superseded'|'failed', prev:null|{kind:'none'|'unlimited'|'cap',cents?},
             appliedAt|null, endedAt|null, note|null }
```
Rules: target = effective cap at activation + extra. At activation remember the user's own previous limit (`prev`) and set the personal cap. At expiry restore `prev`
(none -> delete the personal limit; unlimited -> null; cap -> cents) **only if the personal cap still equals `targetCents`**, otherwise mark `superseded` and leave it. No cap to extend -> `failed`.
One live (scheduled/active) override per user+period at overlapping times (409). Duration 1 hour to `cfg.maxOverrideDays`. Reason 3-200 chars required. System actions use the system key.

## Coach (`api/lib/coach.mjs`): `buildCoach({ user, budgets, detail, range, catalog, overrides }) -> { summary, insights:[Insight] }`
`Insight = { id, severity:'info'|'medium'|'high', category:'model'|'reliability'|'budget'|'telemetry', title, description, action|null, impact|null }`. Rules use only real data
(model mix, outcomes, budget pace). Always include the `telemetry` info insight that token/cache coaching needs client telemetry (not yet available).

## HTTP API (`api/server.mjs`). JSON. Errors: `{ error }` with 400/401/403/404/409/429/5xx
Open reads (need a session only if `APP_VIEW_ACCESS=admin`):
- `GET /api/health` -> `{ gateway:bool, usage:{source, ok:bool|null}, demo:bool, accounts:bool, viewAccess, admin:{email,name}|null }` (never needs a session)
- `GET /api/users?range&data` -> `{ range, data, demo, usage:{source,ok}, buckets[iso], users:[{sub,email,name,requests,ok,failed,lastSeen,models[],spark[],budgets,overrides:[Override(live only)]}] }`
- `GET /api/users/:sub?range&data` -> existing detail shape (`user`, `orgDefaults`, `series`, `models`, `recent`, `audit`) plus `overrides:[Override]` (all for this user, newest first) and `coach`
- `GET /api/company?range&data` -> existing shape plus `overrides:{active:n, scheduled:n}`
- `GET /api/models?range&data` -> `{ default, models:[{alias,id,label,tier,description,enabled,pricePerMTok,family,pinned}], usage:[{model,requests,ok}] }` (`default` is the alias, `haiku` as shipped; `family` is `sonnet|opus|haiku|null`; `pinned` is whether the entry is what its family alias means for everyone); the response also has `warnings: string[]` (always present): one per family that has an enabled entry but no pinned one (a warning, never an error; also logged at start-up as `catalog.warning`)
- `GET /api/overrides?status=active,scheduled` -> `{ overrides:[Override] }`
- `GET /api/audit` -> `{ events:[AuditEvent] }`
Writes (admin session, header `x-app-token`):
- `POST /api/login {email?,password}` -> `{ token, email, name }` (rate-limited; same error for unknown email and wrong password)
- `PUT /api/users/:sub/budget`, `PUT /api/org/budget` -> `{period, action:'set'|'unlimited'|'inherit', usd?}`
- `POST /api/overrides {sub, period, extraUsd, startsAt?(iso), endsAt(iso), reason}` -> `Override` (201) / `DELETE /api/overrides/:id` -> Override
- `POST /api/internal/tick` -> `{ overrides:{applied,ended,failed}, usage:{ingested[,error]} }`; allowed for an admin session **or** a Google-signed ID token (RS256, verified against Google's JWKS; `iss`, `aud == SCHEDULER_AUDIENCE`, `exp`, `email == SCHEDULER_SA`, `email_verified`). Overrides and usage ingest run on **separate** single-flights.
Budgets shape per period: `{ capCents|null, spendCents, source:'user'|'organization'|'rbac_group'|null, limitId|null, unlimited:bool }`.

## Contract changes made after the adversarial reviews (these supersede anything above)

**HTTP**
- `POST /api/logout` (admin) -> `{ok:true}`: revokes every session of that admin. Restarting the server or rotating `APP_SESSION_SECRET` revokes all sessions. Tokens carry `iat` and a per-account version; the format is opaque.
- `POST /api/overrides/:id/retry` (admin) -> `Override`; 409 unless the override is `failed`, still inside its window and not overlapping another.
- `GET /api/health` -> `{ gateway, usage:{source,ok}, demo, accounts, viewAccess, maxOverrideDays, admin, auth:'session'|'iap', identity:{email,name,admin}|null }` and nothing else (`auth`/`identity` added by the enterprise edge release, see below). Probes are cached ~10 s.
- `GET /api/company` adds `usersWithOverrides` (people with a personal cap) and `overrides.overdue`. `userOverrides` counts people, not limit rows.
- `GET /api/users/:sub` adds `auditTruncated:bool` (the gateway's audit endpoint returns at most 500 events and cannot be paged).
- Override adds `overdue`, `overdueMs`, `retryable`, `baseSource`. An override whose creator is no longer an admin is cancelled/reverted (note `creator removed`) when accounts mode is on.
- Errors: gateway unreachable -> `502 {"error":"gateway unavailable"}` with `Retry-After` (never 500); overload -> 503; login throttle -> 429 with `Retry-After`; a budget write for a user the gateway has never seen -> 404; invalid `range`/`data` -> 400; non-plain-decimal money (`0x10`, `1e3`, more than 2 decimals) -> 400.
- Reads are cached 8 s (every write clears the cache), identical in-flight requests are coalesced, at most 4 expensive computations run at once.

**Environment**
- New: `SCHEDULER_AUDIENCE` (required whenever `SCHEDULER_SA` is set; must equal the app's own URL and the Scheduler job's OIDC audience), `APP_DEV=1` (enables the Expo dev CORS origins; never on Cloud Run), `APP_DEMO_ALLOW_CLOUD=1` (demo mode is otherwise refused on Cloud Run), `APP_READ_CACHE_MS`, `APP_HEALTH_CACHE_MS`.
- Stricter: admin passwords >= 12 chars, `APP_SESSION_SECRET` >= 32 chars (required on Cloud Run, may be derived from `GATEWAY_JWT_SECRET` locally), `APP_MAX_OVERRIDE_DAYS` must be a number 1-365 or the server refuses to start, `GATEWAY_SYSTEM_WRITE_KEY` is required in accounts mode (no fallback to an admin key).
- Optional: `USAGE_LOGS_VIEW` (`projects/<id>/locations/<loc>/buckets/<bucket>/views/<view>`, validated) makes the logs backend read a Cloud Logging view limited to the gateway's logs instead of the whole project (Terraform `scope_app_log_access = true`). `SECRETS_HASH` / `CONFIG_HASH` are Terraform-set values whose only job is to roll a new Cloud Run revision when secrets or config change; the app ignores them.

**Gateway event formats (verified against the real gateway by the e2e suite)**
- A spend-cap block is its own event and has **no** `inference` event: `{"evt":"spend.blocked","request_id","sub","cause":"over_limit","cap_cents","source","period"[,"load_test"]}`. The usage backends count it as a 429 with an empty upstream (`spend_cap`); alerts must key on `evt="spend.blocked"`.
- Policy-rejected requests are logged with `model: null`.
- Session tokens are HS256 JWTs (`sub,email,name,aud=claude-gateway,iat,exp,iss=public_url`).

**Overrides invariant.** After a chain of boosts ends, the user's personal cap equals what it was before the first boost began (or none). A boost never activates while another boost for the same user and period is active or mid-activation; it waits and retries. If the org default changes mid-boost, a boost layered on the default is re-targeted to the new default plus the boost; a boost layered on a deliberate lower personal cap restores that cap exactly. A hand edit during a boost makes it `superseded` and is never overwritten.

**Storage.** Only a missing file/object means "empty"; any read or parse error fails loudly (`StoreError`, HTTP 500 generic) and a corrupt file is quarantined as `<name>.json.corrupt-<ts>`. Usage day documents are v2 (counts plus a ledger of hashed request ids so replays after a failure are no-ops); recent requests are per-user rings across 256 shard documents (`usage/recent/<00..ff>`); p50 is approximate (log-spaced bins with interpolation) and ignores missing latencies.

**Usage backend.** `ingest()` throws on failure (the route reports `usage:{ingested:0,error}` without failing the override tick); `usage.status()` exists on the logs backend. ClickHouse mode would need `clickhouse/views.sql` to union `spend.blocked` into `v_gateway_requests`.

**Sessions, login throttling and concurrency (round 2).** Admin sessions, logout revocation and login throttling live in the memory of one app process: a restart, a deploy, or rotating `APP_SESSION_SECRET` signs everyone out, and with more than one instance a logout or a lockout only applies to the instance that handled it, so run the app with exactly one instance (the Terraform default, `max_instances = 1`). Login failures lock per (account, client address) and per client address; a per-account ceiling (50 failures in a rolling hour) logs `admin.login.suspicious` and slows that account by 1.5 s but never blocks a correct password from a clean address. Behind a load balancer the last `X-Forwarded-For` hop is the balancer's own address, so every client then shares one per-address login bucket (10 failures lock it); the per-(account, address) and per-account protections still work, but give the app a direct client address if you can. New log events: `admin.login.suspicious`, `admin.logout`; `admin.login.failed.reason` is `bad_credentials` or `throttled`. Four workers serve expensive reads: anonymous callers can use three (48 queue slots), admins all four (16 reserved slots), then 503 with `Retry-After`; `GET /api/users/:sub` answers 404 from a cached known-users set without building the detail. Only origin-form request targets are served; anything else is a JSON 400.

**Model catalog (`config/models.json`, byte-identical copy `client/models.json`).** One list of entries `{alias, id, label, tier, description, enabled, pricePerMTok, family?, pin?}`; `tier` is `default|upgrade|fast|previous` (free text is allowed). Ships Haiku 5.5 (`haiku`, tier `default`, the default and the Haiku pin), `sonnet-4-6` (`claude-sonnet-4-6`, tier `previous`, the Sonnet pin and allowed by name), Sonnet 5.5 (tier `previous`, allowed by name, not pinned), Opus 5.5 (tier `upgrade`, the Opus pin) and `opus-4-6` (`claude-opus-4-6`, tier `previous`, not pinned). The default model must be enabled in Vertex Model Garden or every session fails. Rules, enforced by every parser (`api/lib/config.mjs` `normalizeCatalog`, `terraform/modules/gateway_config`, the installer `.sh`/`.ps1`, the app's `catalogProblems`; all refuse the same catalogs with a clear message):
- Every enabled entry is allowed (`availableModels`, the `default` entry first). `default` is an alias or id of an existing, enabled entry; omitted means the first enabled entry. Aliases (case-insensitive) and ids are unique.
- `family` is `sonnet|opus|haiku` (default: the alias when it is one of those, else none). `pin` is a bool (default: true only when alias == family, and only while enabled). Only a pinned, enabled entry sets `ANTHROPIC_DEFAULT_<FAMILY>_MODEL`. At most one pinned entry per family. `pin: true` needs a family and `enabled`.
- The installer fails closed: an invalid catalog stops every command before anything is written, so a bad catalog never removes or loosens the lock. A person's own choice (`model <alias|id>`, `install --model <alias|id>`) is the user-level `model` setting (the full id), allowed because it is in `availableModels`; it never touches the pins. The installer's default model is `defaults.json` `model` if set (now optional and absent from `client/defaults.json`), else the catalog `default`.
- Recipe "make Sonnet 4.6 the default": `"default": "sonnet-4-6"`, swap the tiers (`sonnet-4-6` takes `default`, `haiku` becomes `fast`) and reword the descriptions; the pins do not change (`tests/e2e/lib/config.mjs` `sonnet46Default`; the app's Models page offers it as `switchDefaultRecipe`). Recipe "run 4.6 as the default for everyone" (older catalogs where Sonnet 5.5 is the default and pin): `"default": "sonnet-4-6"`, `"pin": true` on `sonnet-4-6` and `opus-4-6`, `"pin": false` on `sonnet` and `opus`, and swap their `tier` values (4.6 takes `default`/`upgrade`, 5.5 becomes `previous`) and descriptions; `previousRecipe` offers that one only while the default's own family has a `previous` entry waiting. Recipe "also run Opus 4.6 as the Opus pin": `"pin": true` on `opus-4-6`, `false` on `opus`, tiers swapped. Tested in api, app, terraform, installer and e2e (`recipe46`). The gateway policy (`terraform/modules/gateway_config/gateway.yaml.tftpl`) sets `model` to the default entry's id (and lists it first in `availableModels`): Anthropic documents that `availableModels` alone does not change a gateway session's default (the Opus the `opus` alias resolves to), and a managed `model` outranks a person's own `model` setting. So `terraform apply` moves everyone's starting model; the installer machine policy and a person's own file are refreshed by the rebuilt installer's `update` and `downgrade`/`reset`. A stamped installer carries its own catalog copy: after a catalog change rebuild it (`scripts/package-client.sh`, with `client/models.json` copied from `config/models.json`) and redistribute.
- Name rules (installer, `package-client.sh`): alias `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`; id `[A-Za-z0-9][A-Za-z0-9._@:/-]{0,127}` (Vertex forms like `claude-sonnet-4-5@20250929`); both reach JSON only through an encoder. `default` of `null`/`""` is refused by every parser. The installer, `/api/models` and the Models page warn about a family with entries but no pin. `client/defaults.json` may hold `gatewayInternalNetworks` (validated like Claude Code does; written into the system policy only when declared; honoured by Claude Code only from a managed source on the machine).
- `GET /api/models` adds `family` and `pinned` per entry (see above). The coach treats a `previous` entry by its family (Opus 4.6 is premium-class, the Sonnets are routine-class, and Haiku 5.5 carries the `default` tier as shipped); only the premium class triggers the "most requests go to Opus" insight, which advises the catalog default (Haiku 5.5 as shipped) for routine work, and the "you have not tried the fast model" nudge exists only for a catalog entry whose tier is `fast` (none as shipped); when a person used more than one premium model the insight names the family ("Opus models") and lists the models, never one model's name next to the sum; `"default": null` or `""` is refused like the installer and Terraform do (omit the key for "first enabled entry"); the demo backend follows the pins (a profile's `sonnet` means the entry pinning sonnet).
- Vertex serves Claude 4.6 from `global`, `us-east5`, `europe-west1`, `asia-southeast1` (not `europe-west2`). `terraform/model_regions.tf` has a `check` that warns (never errors) when an upstream region is outside that list while a 4.6 entry is enabled. `vertex_region` still defaults to `global`.

## Enterprise edge contract
Added by the "enterprise edge" release (Claude 4.6 models, the budget app behind Google IAP, the gateway on an internal load balancer). Each owner appends a subsection; deviations from the brief are listed at the end of the subsection.

### Budget app behind Google IAP (`APP_AUTH_MODE=iap`; `api/lib/{iap,auth,routes,config,gateway}.mjs`, `api/tick.mjs`)
**Why.** The browser talks to ONE origin: browser origin == `Host` the app receives == `APP_ALLOWED_HOSTS` / origin allow-list == the IAP audience's service. IAP's identity is an ambient cookie, so the signed JWT is verified AND every write needs same-origin proof.

**Environment** (`api/lib/config.mjs`; validated at start-up, the process refuses to start on any error)
| Variable | Meaning |
|---|---|
| `APP_AUTH_MODE` | `session` (default when UNSET: password sessions, unchanged) or `iap`. Set-but-empty is a start-up error (an empty template value must not silently pick a mode). The mode is logged at start-up (`auth`). |
| `IAP_AUDIENCE` | Required in iap mode. Exactly `/projects/<PROJECT_NUMBER>/locations/<REGION>/services/<NAME>` (Cloud Run direct IAP) or `/projects/<PROJECT_NUMBER>/global/backendServices/<ID>` (load balancer): the project NUMBER. Compared with `aud` for exact equality. |
| `IAP_ALLOWED_DOMAINS` | Optional comma list (deduplicated, lower-cased). Unset = no extra check; set but listing nothing (`""`, `" , "`) is a start-up error. When set, BOTH the email's domain and the `hd` claim must be listed (a consumer account with a corporate-looking address has no `hd`). |
| `IAP_PUBLIC_KEYS_URL` | Local emulator only: `http://127.0.0.1`, `http://localhost` or `http://[::1]`. Setting it on Cloud Run is a start-up error. Default `https://www.gstatic.com/iap/verify/public_key-jwk`. |
| `APP_ADMINS` | Required in iap mode (the shared-password mode does not exist there). `[{email, name?, writeKey, password?}]`: `password` is optional and unused. Admin = verified IAP email equals an entry (case-insensitive); everybody else who passes IAP is a viewer. |
| `APP_SESSION_SECRET`, `SCHEDULER_SA`, `SCHEDULER_AUDIENCE` | Not needed / ignored in iap mode (no app sessions; IAP blocks the scheduler's own token, the Cloud Run job ticks). |
| `GATEWAY_AUDIENCE` | Empty (or blank) = send NO `Authorization` to the gateway (internal load balancer mode, Cloud Run's own IAM check is off for the gateway). Only the `x-api-key` admin key is sent. |
| `GATEWAY_CA_PEM` | Optional PEM text (certificates only; literal `\n` accepted). For an `https://` `GATEWAY_URL` the app calls the gateway with `node:https` and trusts ONLY this PEM; the certificate's name must still match the URL. Ignored for `http://`. |
`cfg.inCloud` is true for `K_SERVICE` (service) and `CLOUD_RUN_JOB` (job). The tick job must therefore get the same environment as the service (it runs `loadConfig` too: in iap mode `IAP_AUDIENCE` and `APP_ADMINS` are required there as well). On Cloud Run `GATEWAY_URL` must be `https://` (the app sends the gateway admin keys); plain http is accepted only for `localhost`/`127.0.0.1`/`[::1]`. Admin emails are trimmed and lower-cased; the same email twice (after that) is a start-up error. An IAP app on Cloud Run does not accept `Host: localhost`/`127.0.0.1`/`[::1]` unless listed in `APP_ALLOWED_HOSTS` (session mode keeps them for `gcloud run services proxy`).

**Request pipeline in iap mode** (`api/lib/routes.mjs`, in this order)
1. `GET|HEAD /healthz` -> `200 ok`, no auth, no Host check (Cloud Run probes carry the instance address). Static files are served as before (not secret).
2. Target and `Host` checks (unchanged: `APP_ALLOWED_HOSTS` / suffixes; a custom domain must be listed), then the existing cross-origin refusal: an `Origin` that is not `http(s)://<Host>` or allow-listed -> 403 on any method.
3. Fetch Metadata, for every `/api/*` request of every method: `Sec-Fetch-Site` `cross-site`, `same-site` or any unknown value -> **403** before the JWT is looked at (reads included: no cross-site probing or timing of e.g. `/api/users/<sub>`). `same-origin`, `none` and an absent header pass this step. Every API response carries `Cross-Origin-Resource-Policy: same-origin`.
3b. Every `/api/*` request (including `/api/health`, `/api/login`, `/api/internal/*`) needs a valid `x-goog-iap-jwt-assertion`: otherwise **401** (viewers get nothing even with `APP_VIEW_ACCESS=open`: the JWT is the perimeter). If Google's key set cannot be had at all: **503** with `Retry-After`.
4. Non-GET/HEAD requests also need all of: header `x-app-csrf: 1` (exactly); an `Origin`, when sent, equal to `https://<Host>` (`http://<Host>` only off Cloud Run) or in `APP_ALLOWED_ORIGINS`; and at least ONE browser-supplied same-origin proof: such an Origin, or `Sec-Fetch-Site: same-origin` (`none` is not a proof for a write). A write with only the custom header and neither is refused: a browser always sends one of them on a same-origin write. Otherwise **403**. A non-admin on a write route gets **403** `only admins can do this`.
5. `APP_VIEW_ACCESS=admin`: reads need an admin (viewers: **403**).
6. `POST /api/login` and `POST /api/logout` -> **410** (there is exactly one way in). `x-app-token` and `Authorization: Bearer` session tokens are ignored. `POST /api/internal/tick` needs an admin (IAP + CSRF); scheduler ID tokens are not accepted.
`/api/health` reports `auth: 'iap'` and `identity: {email, name, admin}` (`admin: {email,name}|null` as before). The UI shows no login form in iap mode and sends `x-app-csrf: 1` on every write.

**Token rules** (`api/lib/iap.mjs`; the unsigned `x-goog-authenticated-user-*` headers are never read, and are logged once as `iap.misconfigured` if they appear without a valid JWT). `alg` must be exactly `ES256` (no `none`, HS*, RS*; `crit` refused; `kid` required); signature is JWS raw `r||s` (64 bytes, `dsaEncoding: 'ieee-p1363'`); `iss == https://cloud.google.com/iap`; `aud` a string equal to `IAP_AUDIENCE`; `exp`/`iat` numbers with 30 s skew and `exp - iat <= 660 s`; `sub` a non-empty string; `email` a plausible address (and `email_verified` not false). Keys: cached 1 h, stale copy used for up to 6 h when Google is unreachable (then 503), an unknown `kid` triggers at most one refetch a minute after a successful fetch (after a FAILED fetch the retry floor is 5 s and an unknown `kid` is answered **503**, never 401, so a failure at a Google key rotation neither locks the new key out nor tells people they are not allowed); fetch has a 4 s timeout, `redirect: 'error'`, 64 KB cap, only P-256 `use=sig` keys are kept. Logs carry reasons (`iap.denied`, one per reason per minute), never a token.

**Tick job** (`api/tick.mjs`, same image: `node api/tick.mjs`). Builds the same deps as the server, runs the overrides tick and the usage ingest once (separately, so one cannot block the other), prints JSON lines `{evt:"tick.job", phase:"start"|"overrides"|"usage"|"config"|"done", ok, ...}` and exits 0 on success, 1 on a config error, an overrides-tick error, an ingest error or the hard timeout (`TICK_TIMEOUT_MS`, default 240000). Overrides that end up `failed` are data (counted in the `done` line), not a job failure. It fails closed: on Cloud Run (`CLOUD_RUN_JOB`) without `APP_STATE_BUCKET` (the service's store; the file fallback would be an empty local directory that ticks nothing and reports success) it prints `phase:"config", ok:false` and exits 1; the `done` line carries `store: "gcs"|"file"|"memory"`. The entry-point guard compares real paths, so starting it through a symlinked directory still runs it. Safe to run next to the service (the overrides code guards itself in the store). Cloud Scheduler starts the job through the Run API (`POST https://run.googleapis.com/v2/projects/<p>/locations/<r>/jobs/claude-budget-tick:run`).

**Admin identity is the verified email, nothing more.** `APP_ADMINS` entries match on the verified IAP `email` claim only; the `sub` namespace (`accounts.google.com:<id>`) is not checked. That is acceptable here because IAP in front of Cloud Run is gated by IAM members (Google identities only), so a token can only carry an email Google itself vouches for; it would NOT be acceptable if IAP were switched to Identity Platform / external identities (where anyone can register any address), so do not enable that without first requiring the Google `sub` prefix and rejecting a `gcip` claim. The usual email-allow-list caveat applies as well: an address reassigned to a new person (new `sub`) inherits that person's admin rights, so remove admins from `APP_ADMINS` when they leave.

**Deviations from the brief / decisions to know about**
- `/api/health` needs the IAP JWT too (401 without): it exposes gateway/usage state and is the UI's identity call. Probes use `/healthz`, which is new and unauthenticated in every mode.
- `IAP_ALLOWED_DOMAINS` requires `hd` as well as the email domain; `IAP_AUDIENCE` is validated against the two known forms; `IAP_PUBLIC_KEYS_URL` on Cloud Run is an error, not silently ignored.
- Key-set outage is 503, not 401 (so people are not told they are "not allowed" during a Google outage).
- The tick job fails (exit 1) when the usage ingest fails, unlike the HTTP tick, which only reports it.

### The edge on a laptop (`scripts/edge.sh`, `scripts/edge/*`, `tests/e2e/l6-edge.test.mjs`)
Same topology as the deployment, no cloud access: `browser -> IAP emulator -> app (iap mode)` at `http://app.localhost:<port>` and `Claude Code -> ILB emulator (TLS) -> real gateway` at `https://gateway.localhost:<port>` (`*.localhost` is loopback, so origin == Host is exercised for real). **The emulators are not Google**: they prove our wiring (one origin, JWT checks, CSRF defence, TLS trust, `public_url` vs `Host`), not Google's behaviour. Real IAP, the real internal Application Load Balancer, real certificates and Claude Code's leaf pinning are unverified until deployed.
- `scripts/edge/iap-emulator.mjs`: no cookie -> 302 to its own `/_iap/signin` (JSON callers 401); strips client `x-goog-*` / `x-forwarded-*`; forwards with `Host` preserved plus `x-goog-iap-jwt-assertion` (ES256, `iss https://cloud.google.com/iap`, configurable `aud`, 600 s life, `kid`, `email`, `sub accounts.google.com:<n>`, `hd`) and the unsigned `x-goog-authenticated-user-*` headers. Per-run EC key; JWK set at `/.well-known/iap-keys.json` (the app's `IAP_PUBLIC_KEYS_URL`). `?secure_token_test=<bad-signature|expired|wrong-aud|wrong-iss|wrong-alg|unknown-kid|too-long|no-email|garbage|none>` (bare = bad signature) sends a broken token and is not forwarded.
- `scripts/edge/ilb-emulator.mjs`: https (TLS 1.2+) from `scripts/edge/make-certs.sh` (throwaway CA + leaf under `data/edge/`, SAN `gateway.localhost`, `localhost`, `127.0.0.1`, `::1`, 397 days), `Host` kept, `X-Forwarded-For: <supplied>,<client>,<lb>`, `X-Forwarded-Proto: https`, optional `--allow-cidr` (stand-in for firewall rules). The gateway runs with `listen.public_url` = the https URL, plain http on loopback behind it, and `listen.trusted_proxies` covering loopback.
- `scripts/edge/idp-emulator.mjs`: a local OIDC IdP with a pick-a-person page (and a fake Google STS so the gateway's Vertex upstream can run in `load_test_mode`); `scripts/edge/prepare.mjs` renders the gateway config and the app environment (the variables of the contract above, `GATEWAY_URL=https://gateway.localhost:<port>`, `GATEWAY_AUDIENCE` empty, `GATEWAY_CA_PEM` = the generated CA).
- `scripts/edge.sh check` is a 28-step curl walk-through (PASS/FAIL per step), `scripts/edge.sh claude` starts Claude Code with its own config dir and the throwaway CA; the manual version and the proves/cannot-prove table are in docs/LOCAL-DEV.md.
- Ports: `edge.sh` 19330-19334 (override with `EDGE_*_PORT`), L6 19270-19284. State in `data/edge/` (gitignored); the gateway uses its own database `gateway_edge` on the compose Postgres (or `EDGE_POSTGRES_URL`).

### Models: Claude 4.6, family/pin (`config/models.json`, installers, Terraform, app)
Contract above ("Model catalog"). Decisions and deviations to know about:
- Thinking effort is one global setting (`effortLevel` in the engineer's `~/.claude/settings.json`; Terraform `client_default_effort`, shipped `medium`), not per model.
- `client/defaults.json` no longer sets `"model": "sonnet"`. The installer's built-in default for `model` is now empty, so the catalog `default` decides; with the old value the recipe could not move new installs (a `defaults.json` model overrides the catalog). A `model` key in `defaults.json` is still honoured as an override.
- `default` in the catalog may be an id as well as an alias (the installer always accepted both; the API and Terraform now do too, and the API reports the alias).
- The API and Terraform now REFUSE entries without an id/alias (the API used to drop them silently) and a catalog whose `default` is unknown (the API used to accept it, leaving the UI without a starting model).
- `tier: "previous"` entries are not the `upgrade` target and never the default unless chosen; the installer's `upgrade` still means the first `upgrade`-tier entry (Opus 5.5 as shipped). Under the Opus 4.6 recipe swap the `tier` values too if `upgrade` should go to Opus 4.6.
- PowerShell installer: kept in sync by reading only (untested). It also gained `continue` after each option in the argument `switch -Regex`, because without it the catch-all `'^-'` branch fired for every known option too.
- `modelColor` (app/src/theme.tsx): Sonnet 4.6 and Opus 4.6 have their own series colours (Sonnet 4.6 shared Sonnet 5.5's colour before, which made two bars in one chart indistinguishable).
- Terraform's `client_defaults` output (and the file `write_client_defaults` writes) now has exactly the installer's accepted shape `{gatewayUrl, model: "", effortLevel, userSettings: {}}` (it used to carry `defaultAlias`, `defaultModel`, `effort`, `models`, which the installer rejects as unknown keys); `model` stays empty so the catalog default decides. `terraform/tests/run.sh` feeds the output to the installer's own validation (`print-managed --defaults`).

### Terraform: IAP, internal load balancer, BigQuery (`terraform/edge_*.tf`, `tick_job.tf`, `analytics.tf`, `terraform/examples/`)
Variables (all default to today's trial topology; with the defaults the plan of every existing resource is unchanged): `app_access` (`iam`|`iap`), `app_domain`, `app_viewers`, `iap_allowed_domains`, `iap_oauth_client_id`/`iap_oauth_client_secret`, `iap_launch_stage`, `project_number`; `gateway_exposure` (`run_app`|`internal_lb`), `gateway_hostname`, `gateway_dns_zone` (+ `gateway_dns_zone_create`), `lb_subnet_cidr`, `proxy_only_subnet_cidr`, `lb_ip`, `lb_allow_global_access`, `gateway_tls` (`self_signed`|`provided`; the provided private key is the separate sensitive `gateway_tls_key_pem`; `gateway_tls_early_renewal_hours`), `gateway_internal_networks`, `gateway_allow_cidrs`; `analytics` (`logging`|`bigquery`) + `analytics_view`, `analytics_readers`, `analytics_retention_days`, `analytics_include_emails`; `app_security_policy`, `iap_create_agent_with_gcloud`. Outputs: `edge_next_steps`, `iap_audience`, `gateway_ca_pem`, `gateway_cert_expires`, `gateway_lb_ip`, `app_lb_ip`, `analytics_next_steps`; `app_url`/`gateway_url`/`proxy_command` follow the topology.
- `app_access = "iap"`: app env gets `APP_AUTH_MODE=iap`, `IAP_AUDIENCE` (project NUMBER from `data.google_project`, or `project_number`), optional `IAP_ALLOWED_DOMAINS`; `SCHEDULER_SA`/`SCHEDULER_AUDIENCE` and the scheduler `custom_audiences` are dropped; nobody holds `run.invoker` on the app except IAP's service agent; `roles/iap.httpsResourceAccessor` goes to admins + `app_viewers` (on the Cloud Run service, or on the backend service with `app_domain`). Direct IAP = `iap_enabled` on the Cloud Run service (needs the Google provider 7.30+; GA since 2026-03-13, so `iap_launch_stage` defaults to `GA` and `launch_stage` stays unset; `BETA` is opt-in), ingress `ALL`. Direct IAP: `APP_ALLOWED_HOSTS` = Cloud Run's deterministic host `claude-budget-app-<project number>.<region>.run.app` (also what `app_url` prints; no `.run.app` suffix wildcard in IAP mode). With `app_domain`: global external Application LB + managed certificate, ingress `INTERNAL_LOAD_BALANCER`, `APP_ALLOWED_HOSTS` = domain and `APP_ALLOWED_ORIGINS` = `https://<domain>` (the run.app URL is switched off with `default_uri_disabled`), `IAP_AUDIENCE` = `/projects/<number>/global/backendServices/<generated id>`. External or no-organisation users of direct IAP need a custom OAuth client bound to the service with `gcloud iap settings set` (a console/gcloud step printed by `edge_next_steps`; Terraform does not set it). The gateway's regional backend service uses `protocol = "HTTP"` (Google's internal ALB + Cloud Run guide).
- The tick becomes Cloud Run job `claude-budget-tick` (same image, `node api/tick.mjs`, same env and secrets as the app, one shared local) started once a minute by the existing scheduler job through `POST https://run.googleapis.com/v2/projects/<p>/locations/<r>/jobs/claude-budget-tick:run` with an OAuth token of `claude-scheduler` (`roles/run.invoker` on the job). Monitoring: the heartbeat metric counts `tick.job` / `phase=done` lines of the job, the error metric adds `ok=false` and job `severity>=ERROR`, and an alert watches failed job executions.
- `gateway_exposure = "internal_lb"`: regional internal Application LB (proxy-only subnet, LB subnet, reserved internal IP, serverless NEG, backend, URL map, regional certificate, HTTPS proxy, forwarding rule, private Cloud DNS zone for exactly the hostname + A record). Gateway ingress `INTERNAL_LOAD_BALANCER`, `invoker_iam_disabled = true`; `public_url` is derived (`https://<gateway_hostname>`, an explicit different value is refused). App env: `GATEWAY_URL=https://<hostname>`, `GATEWAY_AUDIENCE=""`, `GATEWAY_CA_PEM`; the app and the job get a route into the VPC. The gateway's own run.app URL is switched off (`default_uri_disabled`; the NEG and the app's `https://<hostname>` call do not use it). `gateway.yaml`: `listen.trusted_proxies` = `169.254.0.0/16` + the load balancer's forwarding-rule range (`lb_subnet_cidr`, or `lb_ip`/32) + the proxy-only subnet (the gateway takes the right-most untrusted `X-Forwarded-For` hop, and Google appends `<client>,<load balancer address>`, so the forwarding-rule address must be trusted or every engineer resolves to the load balancer); `access_control.allow_cidrs` only when `gateway_allow_cidrs` is set (IPv4, no /0, `cc-gateway-subnet` added automatically because the app and the tick job call from there). A log metric + alert watch the gateway's `access.public_client` event. Cross-checks in `terraform_data.edge_checks`: lb/proxy-only ranges private, not overlapping each other or `cc-gateway-subnet`, proxy-only /22-/26, `lb_ip` inside the lb range; a `check` compares them with the Service Networking range after the first apply. TLS: provided PEMs (recommended; key in the sensitive `gateway_tls_key_pem`) or a hashicorp/tls CA (5 years, `max_path_length = 0`) + leaf (1 year, no automatic renewal because a new leaf makes Claude Code re-pin; a `check` warns in the last 60 days); the self-signed CA key is in the state and not name-constrained.
- `analytics = "bigquery"`: raw sink dataset `claude_gateway_logs` (partition expiry `analytics_retention_days`, default the profile's log retention) and a second dataset `claude_gateway_analytics` holding the view `v_gateway_requests` as an authorized view; `analytics_readers` get `dataViewer` on the second dataset only (+ project `jobUser`); no e-mail column unless `analytics_include_emails`.
- Deviations: no `allUsers` fallback for the gateway exists (a plan-wide "no allUsers" test is a security control; if Cloud Run refuses `invoker_iam_disabled` the apply fails and an administrator must allow it); `allow_cidrs` is not rendered by default (a wrong value locks everyone out; the `X-Forwarded-For` layout of the Cloud Run hop is from the gateway's resolver and Google's documentation, not verified on a live deployment); `analytics_view` is a second step because BigQuery creates the sink table lazily; the Google provider constraint moved from `~> 6.0` to `~> 7.30` (+ `tls`; no `google-beta`: the IAP service agent is created by Google when IAP is first used, a best-effort `local-exec` `gcloud services identity create` (fallback `gcloud beta ...`) before the grant, with a documented manual fallback), so existing states need `terraform init -upgrade` and a read of the plan; `public_url` now defaults to null (resolved to `http://localhost:8891`); the wizard has a topology question after the profile.
